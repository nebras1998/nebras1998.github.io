# اختبار الضغط (Load Testing) لمشروع lab-lims باستخدام k6

## 1) التثبيت

k6 أداة CLI مستقلة (ليست حزمة npm للمشروع)، تُثبَّت على جهازك مرة واحدة:

**Windows (الأسهل: winget أو Chocolatey):**
```powershell
winget install k6 --source winget
# أو
choco install k6
```

**عبر npm (إن كنت تفضل عدم التثبيت العام):**
```bash
npm install -g k6
```
(هذا يثبّت غلاف Node ينزّل الثنائي الحقيقي عند أول تشغيل)

تحقق من التثبيت:
```bash
k6 version
```

## 2) في VS Code
لا حاجة لأي إعداد خاص — افتح مجلد `k6-tests` في VS Code، وشغّل السكربتات من الطرفية المدمجة (Terminal) بأمر `k6 run`. إن أردت أزرار تشغيل داخل المحرر، يوجد امتداد اختياري باسم **"k6"** من Grafana Labs في متجر الإضافات، لكنه غير ضروري.

## 3) شغّل المشروع أولاً
```bash
npm run build && npm run start   # محاكاة أقرب للإنتاج، أو
npm run dev                      # للتجربة السريعة فقط (أبطأ وغير ممثّل للأداء الحقيقي)
```
تأكد أن `.env` يشير لمشروع Appwrite **تجريبي/staging وليس الإنتاج**.

## 4) السكربتات المرفقة

| الملف | الهدف | ملاحظة |
|---|---|---|
| `01-smoke-public-pages.js` | فحص أولي خفيف (smoke test) لصفحات عامة | ابدأ بهذا دائماً قبل أي اختبار أثقل |
| `02-portal-booking-rate-limit.js` | اختبار نقطة الحجز العامة `/api/portal/book` | **يتوقّع** رؤية أخطاء 429 بعد 5 طلبات لكل IP خلال 10 دقائق — هذا نجاح للاختبار، ليس فشلاً في الخادم |
| `03-reports-verify.js` | اختبار نقطة التحقق العامة `/api/reports/verify` | حد المعدل هنا أوسع (20/10 دقائق) |
| `04-authenticated-dashboard-stats.js` | اختبار `/api/dashboard-stats` (يتطلب جلسة مسجّل دخول) | يسجّل الدخول مباشرة عبر REST API الخاص بـ Appwrite قبل بدء التكرار |

## 5) طريقة التشغيل
```bash
k6 run 01-smoke-public-pages.js -e BASE_URL=http://localhost:3000

k6 run 04-authenticated-dashboard-stats.js \
  -e BASE_URL=http://localhost:3000 \
  -e APPWRITE_ENDPOINT=https://your-appwrite-endpoint/v1 \
  -e APPWRITE_PROJECT_ID=your_project_id \
  -e TEST_EMAIL=manager@example.com \
  -e TEST_PASSWORD=your_test_password
```
**لا تضع كلمة مرور حقيقية في الكود** — مرّرها دائماً عبر `-e` من الطرفية أو من ملف `.env` محلي يقرأه k6 (أو أداة مثل `dotenv-cli`)، ولا ترفعها لأي مستودع.

## 6) قراءة النتائج
- k6 يطبع ملخصاً في الطرفية مباشرة (p95/p99 لزمن الاستجابة، معدل الأخطاء، إلخ)
- لتصدير تفصيلي: أضف `--out json=results.json` لأمر `k6 run`
- لعرض بياني تراكمي: شغّل Grafana + InfluxDB محلياً (اختياري)، أو استخدم `k6 run --out csv=results.csv` وافتحه في Excel

## 7) تحذيرات خاصة بهذا المشروع تحديداً
- **مسار `api/reports/[id]/pdf` غير مضمّن في هذه السكربتات عمداً**: كل طلب يشغّل متصفح Chromium كاملاً (Puppeteer) على الخادم، وهو مكلف جداً تحت الضغط ويمكن أن يُسقط الخادم بسرعة حتى بأحمال منخفضة (5-10 مستخدمين متزامنين). إن أردت اختباره، ابدأ بـ 1-2 مستخدم افتراضي (VU) فقط وراقب استهلاك الذاكرة/المعالج على الخادم مباشرة.
- حدود المعدل (rate limiters) في الكود مخزّنة في ذاكرة العملية (`Map` داخل العملية نفسها) — نتائج اختبار الضغط ستعكس سلوك نسخة واحدة فقط من الخادم، وليس ما سيحدث خلف موازن حمل بعدة نسخ.
- كل طلب بيانات وهمي (حجوزات تجريبية، إلخ) سيبقى في قاعدة بيانات Appwrite بعد الاختبار — امسحها يدوياً أو أضف بادئة واضحة (مثل `LOADTEST-`) لتسهيل حذفها لاحقاً.
